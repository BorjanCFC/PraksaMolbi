# PraksaMolbi - Систем за електронско поднесување и обработка на студентски молби

PraksaMolbi е веб-платформа за дигитализација на процесот на поднесување, архивирање, административна обработка и одлучување по студентски молби на Факултетот за електротехника и информациски технологии - ФЕИТ.

Системот овозможува јасно дефиниран workflow помеѓу студентите, Архивата, Студентската служба и Продеканот, со поддршка за документи, архивски броеви, интерна комуникација, одлуки, генерирање официјален PDF документ и известување на студентот.

---

## Што е имплементирано

- Студентска најава преку Microsoft Entra ID
- Посебна најава за административни корисници
- Поддршка за повеќе улоги на ист корисник
- Избор на активна улога по најава
- Поднесување студентски молби
- Задолжително прикачување PDF документ
- Архивирање на молбите
- Внесување и дополнителна корекција на архивски број
- Проверка на молбата од Студентската служба
- Интерна комуникација помеѓу Студентската служба и Продеканот
- Одобрување или одбивање на молбата од Продекан
- Повратна информација до студентот
- Генерирање официјален PDF документ
- Email известувања
- Поделба на активни и завршени молби
- Филтрирање на молбите
- Филтрирање по број на индекс
- Responsive приказ за помали екрани
- PostgreSQL база
- Sequelize ORM и migrations
- MVC архитектура

## Студент

Студентот се најавува преку Microsoft Entra ID.

Студентот може да:

- поднесе нова молба;
- внесе наслов на молбата;
- внесе опис;
- избере семестар;
- избере учебна година;
- внесе број на индекс;
- избере насока;
- приложи задолжителен PDF документ;
- ги прегледува само сопствените молби;
- го следи статусот на молбата;
- го преземе приложениот документ;
- го преземе генерираниот официјален PDF документ;
- ја види повратната информација по донесена одлука.

По првото поднесување молба, бројот на индекс и насоката се зачувуваат во студентскиот профил во базата.

При секое следно поднесување:

- бројот на индекс автоматски се пополнува со вредноста од базата;
- насоката автоматски се избира;
- студентот може да ги промени двете вредности;
- доколку вредностите се променети, новите податоци се зачувуваат во базата.

Поддржани насоки на ФЕИТ 2026 се:

- `ЕАОИЕ`
- `ЕЕПМ`
- `ЕЕС`
- `КСИАР`
- `КТИ`
- `КХИЕ`
- `ТКИИ`

## Архива

Архивата е првата административна улога што ја обработува новоподнесената молба.

Архивата може да:

- ги прегледува новите молби;
- ги прегледува податоците на студентот;
- го преземе приложениот документ;
- внесе архивски број;
- го промени веќе внесениот архивски број доколку е направена грешка;
- ги прегледува претходно архивираните молби.

Архивата нема право да ја одобрува или одбива молбата.

По првото внесување на архивскиот број, молбата се проследува до Студентската служба.

Доколку архивскиот број подоцна се измени, се менува само неговата вредност во базата и workflow фазата на молбата не се враќа назад.

---

## Студентска служба

Студентската служба ја добива молбата откако Архивата ќе внесе архивски број.

Студентската служба може да:

- ги прегледува податоците на студентот;
- ја прегледува молбата;
- го преземе приложениот документ;
- го провери архивскиот број;
- внесе интерна забелешка до Продеканот;
- ја потврди административната проверка;
- ја проследи молбата до Продеканот.

Студентската служба нема право директно да ја одобри или одбие молбата.

По донесувањето на одлуката од Продеканот, молбата повторно се враќа кај Студентската служба.

Тогаш Студентската служба може да:

- ја прегледа одлуката;
- ја прегледа забелешката од Продеканот;
- генерира официјален PDF документ;
- го финализира процесот;
- иницира email известување до студентот.

---

## Продекан

Продеканот ја добива молбата откако Студентската служба ќе ја потврди административната проверка.

Продеканот може да:

- ја прегледува молбата;
- ги прегледува податоците на студентот;
- го преземе приложениот документ;
- ја види забелешката од Студентската служба;
- ја одобри молбата;
- ја одбие молбата;
- внесе повратна информација до студентот;
- внесе интерна забелешка до Студентската служба.

По донесување на одлуката, молбата повторно се проследува до Студентската служба за генерирање на официјалниот PDF документ.

---

## Администратор

Администраторот има глобален административен пристап до системот.

Администраторот може да:

- ги прегледува корисниците;
- ги прегледува молбите;
- доделува административни улоги;
- управува со улогите на корисниците;
- додели повеќе улоги на ист корисник.

Администраторот служи како системска административна улога и не е дел од основниот workflow за обработка на молбата.

## Workflow на молба

Секоја молба поминува низ строго дефинирани фази:

```text
Студент
   ↓
Архива
   ↓
Студентска служба
   ↓
Продекан
   ↓
Студентска служба
   ↓
Генерирање PDF
   ↓
Завршена молба
```

Во системот workflow фазите се:

```text
SUBMITTED
ARCHIVED
SERVICE_REVIEWED
DECIDED
COMPLETED
```

### 1. SUBMITTED

Студентот поднесува нова молба.

Во оваа фаза молбата е достапна за Архивата.

Студентската служба и Продеканот сè уште немаат потреба да ја обработуваат молбата.

---

### 2. ARCHIVED

Архивата внесува уникатен архивски број.

По внесувањето на архивскиот број:

- молбата се смета за обработена од Архивата;
- молбата станува достапна за Студентската служба.

---

### 3. SERVICE_REVIEWED

Студентската служба ја проверува молбата и приложените документи.

По потреба може да внесе забелешка до Продеканот.

Со потврдување на проверката, молбата се испраќа до Продеканот.

---

### 4. DECIDED

Продеканот донесува конечна одлука.

Можни статуси се:

```text
Одобрена
Одбиена
```

Продеканот може дополнително да внесе:

- повратна информација до студентот;
- забелешка до Студентската служба.

По донесувањето на одлуката, молбата повторно станува достапна за Студентската служба.

---

### 5. COMPLETED

Студентската служба го генерира официјалниот PDF документ.

По успешно генерирање:

- PDF документот се зачувува;
- молбата преминува во `COMPLETED`;
- студентот може да го преземе документот;
- се иницира email известување до студентот.

Грешка при испраќање email не ја поништува одлуката, генерираниот PDF документ или workflow фазата.

---

## Поддршка за повеќе улоги

Системот поддржува повеќе административни улоги на ист кориснички профил.

На пример, ист корисник може истовремено да има:

```text
Admin
Sluzhba
Prodekan
```

Поврзувањето помеѓу корисниците и улогите е many-to-many.

За таа цел се користи join табелата:

```text
user_roles
```

По најава, доколку корисникот има повеќе административни улоги, се прикажува посебен екран за избор на активна улога.

Избраната улога определува:

- кои молби се видливи;
- кои акции се дозволени;
- кој dashboard ќе биде прикажан.

---

## Dashboard

Dashboard-от се прилагодува според активната улога.

Молбите се поделени во две главни категории:

```text
Активни молби
Завршени молби
```

### Активни молби

Во овој дел се прикажуваат молбите што моментално бараат акција од активната улога.

### Завршени молби

Во овој дел се прикажуваат молбите што веќе се обработени од аспект на активната улога.

За подобар приказ, првично се прикажуваат најмногу 10 завршени молби.

Доколку има повеќе, корисникот може да ги прикаже преку копчето:

```text
Види повеќе
```

---

## Филтрирање

Административните улоги можат да ги филтрираат молбите според:

- статус;
- семестар;
- учебна година;
- број на индекс;
- почетен датум;
- краен датум.

Филтрите се применуваат само по притискање на копчето:

```text
Примени
```

Копчето:

```text
Исчисти
```

ги отстранува активните филтри.

Филтрите се применуваат и на активните и на завршените молби.

---

## Филтер по број на индекс

Филтерот по индекс работи како текстуално пребарување.

На пример, доколку постојат:

```text
106/2022
106/2023
210/2022
115/2022
```

и се внесе:

```text
106
```

ќе се прикажат:

```text
106/2022
106/2023
```

Ако се внесе:

```text
2022
```

ќе се прикажат:

```text
106/2022
210/2022
115/2022
```

Ако се внесе:

```text
106/2022
```

ќе се прикажат молбите од студентот со конкретниот индекс.

## Статуси

Молбата може да има еден од следните статуси:

```text
Во процес
Одобрена
Одбиена
```

Во интерфејсот статусите се визуелно означени:

- `Во процес` - жолто/портокалово;
- `Одобрена` - зелено;
- `Одбиена` - црвено.

## Генерирање официјален PDF документ

По донесување на конечната одлука, Студентската служба генерира официјален PDF документ.

Документот содржи:

- универзитет и факултет;
- датум;
- архивски број;
- број на молба;
- име и презиме на студентот;
- број на индекс;
- насока;
- семестар;
- учебна година;
- опис на молбата;
- конечен статус.

Името на генерираниот документ е во формат:

```text
Molbi-<broj-na-molba>-<ImePrezime>.pdf
```

Пример:

```text
Molbi-12-SandraShandarovska.pdf
```

## Email известувања

Системот поддржува автоматско email известување на студентите.

Email се испраќа:

- по успешно поднесување нова молба;
- по финализирање на одобрена молба;
- по финализирање на одбиена молба.

Испраќањето email е секундарна операција.

Тоа значи дека доколку SMTP серверот не е достапен:

- новата молба сепак се зачувува;
- одлуката останува зачувана;
- PDF документот останува генериран;
- workflow фазата останува зачувана;
- основната операција не се поништува.

## Автентикација

Системот користи различен начин на најава за студенти и административни корисници.

### Студентска најава

Студентите се најавуваат преку Microsoft Entra ID со OIDC Authorization Code flow.

При процесот се користат:

- `state`;
- `nonce`;
- issuer validation;
- audience validation;
- tenant validation;
- Microsoft `oid`;
- email;
- проверка на дозволени email домени.

Студентот нема посебна локална лозинка во апликацијата.

---

### Административна најава

Административните корисници имаат посебен login view.

Административната најава е одделена од студентската Microsoft Entra најава.

Поддржана е интеграција со ФЕИТ серверската инфраструктура, како и локални административни корисници каде што тоа е конфигурирано.

Локалните лозинки се чуваат hash-ирани со:

```text
bcryptjs
```

## Архитектура

Апликацијата е Node.js/Express веб-апликација со server-side rendering преку EJS.

Production архитектурата е:

```text
Кориснички веб-прелистувач
        ↓
molbi.feit.ukim.edu.mk
        ↓
DNS
        ↓
Nginx
        ↓
localhost:3001
        ↓
Node.js / Express
        ↓
PostgreSQL
```

Nginx се користи како reverse proxy пред Node.js апликацијата.

## Microsoft Entra App Registration

За локална студентска најава потребна е Microsoft Entra App Registration.

Основни чекори:

1. Отвори Entra Admin Center.
2. Отвори `App registrations`.
3. Избери `New registration`.
4. Внеси име на апликацијата.
5. Избери account type што одговара на ФЕИТ tenant конфигурацијата.
6. Додади Web Redirect URI:

```text
http://localhost:3000/auth/microsoft/callback
```

7. Од Overview зачувај:

```text
Application (client) ID
Directory (tenant) ID
```

8. Креирај Client Secret.
9. Вредностите внеси ги во `.env`.
10. Конфигурирај ги потребните OpenID Connect permissions.

Основните scopes се:

```text
openid
profile
email
```

## Git и deployment

Локалните промени се commit-ираат и се испраќаат на GitHub.

Основниот deployment процес е:

```text
Локални промени
      ↓
Git commit
      ↓
GitHub
      ↓
git pull на production сервер
      ↓
Sequelize migration
(доколку има нова migration)
      ↓
Restart на molbi.service
```

Пример:

```bash
git pull --ff-only origin main
```

Доколку има нова migration:

```bash
npx sequelize-cli db:migrate --config config/config.js --env production
```

Потоа:

```bash
systemctl restart molbi
systemctl status molbi
```

## Фајлови што не треба да се commit-ираат

Во Git repository не треба да се зачувуваат:

```text
.env
uploads/
backup_*/
__pycache__/
*.pyc
локални helper/patch скрипти
```

Чувствителни податоци како:

- лозинки;
- database credentials;
- Microsoft Entra Client Secret;
- SMTP лозинки;

не треба да бидат запишани директно во source code или README.
